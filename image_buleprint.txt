Minimal image-source expansion blueprint

Goal
- Support multiple section image sources, not just photos.
- Keep the current architecture as much as possible.
- Avoid loading every full-resolution image into the renderer at once.
- Use a consistent 3-tier strategy:
  - thumb: all sections for the active source
  - standard: visible sections plus a small buffer
  - highres: explicit request only, typically viewer / context action

Core design
- Add a new axis: sourceId.
- Keep the existing depth-scale axis.
- Treat the current photo path as source_1, not as a special case.
- Initial UI can stay simple:
  - active source selector
  - image visibility toggle
- Only one source is actively rendered in the main view at a time.

Data shape
- Current conceptual shape:
  - modelImages[depthScale][sectionKey]
- Proposed conceptual shape:
  - modelImages.sources[sourceId][tier][depthScale][sectionKey]
- Keep sectionKey as the current "hole-section" naming.

Tier policy
- thumb:
  - preload for all sections of the active source
  - very low dpcm
  - used for zoomed-out overview
- standard:
  - lazy-load for visible sections and a small buffer
  - normal dpcm
  - used for normal browsing
- highres:
  - per-section explicit load only
  - existing high-resolution behavior can be reused

Minimal execution flow

Phase 1
- Register one or more image sources.
- Treat existing photo directory as source_1.

Phase 2
- On model load:
  - request thumb tier for all sections of active source
- On normal browsing / scroll:
  - request standard tier only for visible sections plus buffer
- On explicit section open / viewer / high-res action:
  - request highres only for target section

Phase 3
- On source switch:
  - keep already cached thumbs if available
  - request standard only for current visible sections

What not to change
- Do not change LC_modules.
- Do not change plot logic for this feature.
- Do not make every source load at startup in full resolution.
- Do not special-case CT in the data model. Use generic source ids.

Smallest viable implementation order
1. renderer/js/renderer.js
   - setupSettings()
   - initialiseImages()
2. main.js
   - loadCoreImages(loadOptions, type)
   - source registration metadata
3. preload/preload.js and preload/preload_image_viewer.js
   - payload extensions
4. renderer/js/renderer.js
   - loadCoreImages(...)
   - assignCoreImages(...)
   - drawing branch uses active source + tier
5. renderer/js/renderer_image_viewer.js
   - same source-aware structure

Why this is the minimal consistent plan
- It keeps one image-loading backend in main.js.
- It keeps one renderer cache shape.
- It does not require core-logic changes.
- It solves both extensibility and performance at once:
  - source dimension
  - tiered loading
  - visible-range standard loading
